## 2. 工作方法与持续推进

对每项采用：核对规格 → 最小复现/确认 → 明确验收 → 修改 → 定向验证 → 更新正式台账。已有正确实现保留；低风险文案/样式无需堆测试，权限、数据、迁移、治理、失败传播需要能证明缺陷的验证。

每阶段交接写明已完成、未完成、证据和下一步，完成后继续下一阶段。局部外部阻塞不应停止其他独立本地工作。发现新问题先登记范围和影响，再实施相关修复，不无限扩张到重构全站。

不要新增微服务、Redis、WebSocket、支付、组织层级、向量数据库或 AI；不随意更换认证库、数据库框架和 UI 体系。优化必须对应可观察的问题、既有验收缺口或实测预算。


## 3. 每项关闭记录

沿用并强化现有正式审计模式；至少记录以下信息，不另建不受校验的“全部完成”文件：

```text
id / sourceIds / taskIds / priority
originalClaim / dispositionReason
status: pending | in_progress | fixed | accepted_design | not_reproduced | deferred | blocked_external
subitems（适用于复合组，各自有状态与证据）
changedFiles
closureEvidence: 复现、命令、起止时间/时区、实际退出码、环境与源码身份、日志位置及散列
remainingLimitations / nextAction / verifiedAt
```

未验证时 verifiedAt 不虚填为创建日期；状态迁移要保留历史。fixed 必须有实际修复和验证；accepted_design 必须有有效设计依据；not_reproduced 不等于已证明永不发生；deferred/blocked_external 不能算关闭发布阻塞。精确模式由 G1 与现有注册表统一，不为套模板破坏旧材料。
