## 3. 8 个本轮确认问题

### AR-01 · P2 · 看板顶部按钮可以直接丢弃创建草稿

- 位置：`src/features/board/real-board.tsx:310`；`src/features/tasks/real/task-create-form.tsx:367`。
- 复现：点看板顶部“新建任务”，填写标题，再点顶部同一按钮；表单直接卸载，再展开标题为空。对照操作：表单底部“取消”会确认，拒绝后输入保留。
- 实际探针：底部取消确认 1 次，顶部收起确认 0 次，再展开值为空。
- 原因：顶部 `setCreating(!creating)` 绕过 `confirmLeave()`。业务 API 未接收到草稿，丢失不可由刷新恢复。
- 规格：`docs/02-UX-AND-DESIGN.md:159` 明确要求创建的取消、收起、页面离开共用保护。
- 修复方向：收起入口统一调用保护，拒绝时不卸载；保存成功的自动收起仍不额外确认。
- 验收：顶部/底部/导航分别测试拒绝和接受；拒绝保留所有字段，接受只确认一次；保存成功不误弹窗。

### AR-02 · P2 · UI 创建任务的默认优先级违背产品默认值

- 位置：`src/features/tasks/real/task-create-form.tsx:96,117,142`；服务默认值 `src/server/modules/task/create.ts:51`。
- 复现：只填标题，不动优先级，提交实际请求含 `priority: "NONE"`；探针截获了该 body。
- 规格：`docs/01-PRODUCT-SPEC.md:67` 规定默认 TODO/MEDIUM；服务端未传值时也默认 MEDIUM。UI 显式发送 NONE，覆盖了服务端默认值。
- 影响：API 创建与 UI 创建产生不同默认结果，影响优先级筛选与排序。
- 修复方向：初始化和 dirty 基准一起改成产品默认值，或统一复用明确的默认定义；不能只改初始值而使空表单永久 dirty。
- 验收：仅填标题创建后 UI/API 都是 MEDIUM；空表单关闭不确认，手动改成 NONE 后能正常保存。

### AR-03 · P2 · 打开任务会清空尚未应用的筛选输入

- 位置：`src/features/tasks/real/task-filters.tsx:44,67`。
- 复现：在“搜索任务”输入文字，尚未点击应用，导航仅增加 `?task=<id>`；搜索框变空。
- 原因：整个表单以 `search.toString()` 作 key；详情面板参数也引发组件重建，无控输入重置。
- 影响：查看任务这一非筛选操作丢弃用户已输入的搜索词，其他尚未应用的选择也有同类风险。
- 修复方向：只用真正筛选字段构造重置依据，或明确控制本地输入；仍要处理用户主动重置、切换项目及真实筛选条件变化。
- 验收：开关详情保留待应用输入；点击应用才更新查询；主动清空和项目切换按预期重置。

### AR-04 · P3 · 任务上限错误给出无效的处理建议

- 位置：`src/features/tasks/real/task-create-form.tsx:178`。
- 复现：创建返回 LIMIT_EXCEEDED 时 UI 显示“未删除任务已达上限（1000 个），请先清理回收站。”
- 规格：`docs/01-PRODUCT-SPEC.md:9,73` 上限统计未删除任务，已在回收站内的记录不占这个名额，V1 也不提供永久清空功能。
- 影响：用户被引导执行不存在、且不能释放当前额度的操作。
- 修复方向：建议删除不再需要的未删除任务或联系有删除权限的成员；不能承诺“完成任务”会释放额度，DONE 仍是未删除任务。
- 验收：1000 个未删除任务的错误文案与实际可用操作一致；软删除一个任务后可创建，恢复仍重新校验上限。

### AR-05 · P2 · staging 接受会让不同访问者共用认证限流桶的配置

- 位置：`src/server/env.ts:185`；`src/server/auth/options.ts:130–175`；`src/server/http/client-ip.ts`。
- 条件：APP_ENV=staging 且遗漏 TRUSTED_PROXY_COUNT，默认值为 0。production 对此会启动失败，staging 则通过校验。
- 执行结果：合成 staging 配置通过；不同 X-Forwarded-For 值均返回不信任代理的哨兵值，认证 handler 转换为同一 `0.0.0.0`；登录规则为每路径每桶 60 秒 10 次。
- 影响：该配置下多个访问者相互消耗登录/找回密码等限额，可造成其他人的正常请求被拒。**未在真实 staging 发起攻击，也未证明某个部署已使用此配置。**
- 设计边界：拒绝相信任意 XFF 本身是正确的，不能以“直接信客户端 XFF”修复。
- 修复方向：对公网 staging 采用与 production 一致的代理前置条件；确有直连场景则显式设计可验证的来源识别/限制，而非默默沿用全站共享桶。
- 验收：staging 错配启动失败；经过已知代理的不同客户端分桶；同客户端不能伪造头绕过限流；开发直连行为明确。

### AR-06 · P2 · 退出登录先撤销会话，再询问是否放弃草稿

- 位置：`src/features/shell/user-menu.tsx:63,80`。
- 复现：创建表单有草稿时点账户菜单“退出登录”；真实 authClient 已发 sign-out 请求，成功响应后 `location.assign` 才触发 beforeunload 确认。选择留下时，页面仍有草稿，但退出动作已先执行。
- 实际探针：sign-out 请求 1 次，其后才出现离开提示；拒绝后 URL 和标题输入保留。API 成功响应为合成替身，此探针证明请求次序，不宣称用真实用户撤销了生产会话。
- 影响：用户选择保留编辑无法取消已发出的登出；真实成功登出后继续保存会遭遇失效会话，草稿保留保护不完整。
- 修复方向：先完成统一离开确认，再调用登出；取消时不发请求，接受时只确认一次，并保留登出失败的可恢复状态。
- 验收：有草稿且取消时 sign-out 请求数为 0；确认后仅发一次并跳登录；接口失败保留草稿/错误反馈；无草稿直接退出。

### AR-07 · P3 · 成员主动退出缺失批量取消分配数量

- 位置：`src/server/services/member.service.ts:192–194`。
- 源码事实：服务已取消负责人、增加相关 task.version，并写 MEMBER_LEFT/MEMBER_REMOVED 事件；但 `isSelfExit ? {} : { count: affected.count }` 明确对主动退出省略 count。
- 规格：`docs/05-API-CONTRACT.md:127` 要求成员退出的批量取消分配用 metadata.count 表达。
- 影响：主动退出的审计信息不完整。不是“完全没有事件”，也不是需要修改 boardVersion；后者由 `docs/04-DATA-MODEL.md:111` 明确不要求。
- 修复方向：主动退出与移除都写受影响数量，继续遵守 metadata 白名单。
- 验收：0/多项分配的两种退出路径记录准确 count；无额外重复事件；task.version 正确变化，boardVersion 行为保持规格。
- 证据等级：源码与规格确定不一致；未为本项新增写库反例，已有成员流程集成测试本轮通过。

### AR-08 · P2 · 真实看板卡片缺少子任务、评论、附件计数

- 位置：`src/features/board/real-board.tsx:517–614`；对照 `src/features/board/task-card.tsx:106–117`。
- 规格：`docs/02-UX-AND-DESIGN.md:99` 要求看板卡片显示这些信息。
- 实际探针：用通过 TaskSummarySchema 的合成任务，子任务 3/8、评论 7、附件 2；真实 RealBoard 卡片已渲染标题，却没有任何相应计数。DTO 已提供计数，因此不是服务端缺数据。
- 原因：演示用 SampleTaskCard 有计数，生产 RealBoard 自己实现另一张卡片，漏接了这一部分。
- 影响：用户需要逐个打开详情才知道协作内容和子任务进度；演示页面覆盖不能证明真实页面功能一致。
- 修复方向：给真实卡片补齐有可访问文本的计数，必要时抽取两者共享的展示部分，保留真实排序/权限逻辑。
- 验收：非零计数正确显示，零值按设计隐藏；窄屏、长标题、只读和拖拽时布局正常；评论/附件/子任务变化后刷新正确更新。

## 5. 架构、测试与性能的实际判断

### 5.1 当前有证据支持的基础

- 授权在服务端和事务内重查；资源归属、软删除、幂等重放可见性不是只靠前端按钮。
- 项目行锁、task/version、boardVersion、幂等唯一键各有不同职责；真实数据库并发/冲突测试已运行。
- 用户内容经 DTO 白名单与私有缓存控制；附件由服务端鉴权/受约束流式管线处理，未认证上传快速拒绝已通过 HTTP 验证。
- 新构建经过真实 readiness 查询，且同 HEAD 远端容器 smoke 成功；没有证据支持“standalone 必缺 Prisma 引擎”。
- 正式测试具备数据库目标约束、前后内容指纹、零重试浏览器门禁及独立的规划负向探针；本轮没有把历史日志当作今天重跑。

### 5.2 应继续完善，但不能冒充已发生缺陷的部分

1. **故障注入的粒度。** 当前有业务失败/冲突后无残留断言，不是零回滚覆盖；但应补真正“已经修改 Project/Task，随后 Activity 或 Idempotency 写入失败”的定点回滚，验证多表、计数、版本一起恢复。先写真实 DB 反例，不能只 mock `$transaction`。
2. **前端验收与真实页面同步。** AR-01/02/06/08 显示演示卡片、组件局部流程与正式页面存在分叉。补测试应覆盖用户操作组合和规格默认值，而不是复制实现。没有理由为了 8 个边界点再造大型框架。
3. **性能覆盖。** 可以把三列资源计数合批、核查重复 RSC 授权查询，但应保留一致快照与授权隔离。为 due/priority 排序、真实认证限流写放大、混合附件流量补实际测量，再决定索引和聚合。不得引入跨用户共享缓存来省查询。
4. **容量保护。** 每用户上传并发、大小/配额/总时限和代理限制已有；跨用户总上传临时空间、下载并发、进程异常后临时残留仍值得在小机器上测量。没有现场负载数据就不能断言必然 OOM，也不能把 per-user 控制描述成“完全无限制”。
5. **API 一致性。** comments GET 无效分页仍返回英文通用消息且没有字段细节；任务 DELETE 使用较宽松的数字 coercion，而评论/子任务 DELETE 使用正十进制版本 schema。后者的严格语法在现文档只明确给评论/子任务，先统一产品协议再改实现，不能把接受 `1e0` 直接称为越权。均作为低优先级收敛项，未混入 8 个明确规格缺陷。
6. **限流窗口与上线监控。** 增加 HTTP 全链路到期恢复探针，并在真实生产配置健康失败、错误率/延迟、磁盘/备份失败的可执行告警。已有底层窗口测试和路由拒绝测试并不证明全部端到端恢复情形。
7. **数据库不变量。** 对跨行配额的保护不能靠普通 CHECK 凭空解决；position 的正式排序键是 `(position,id)`，不能随手加唯一索引破坏重新编号过程。未来新增写路径应复用锁入口并有竞争测试；若需要唯一约束，先设计延迟约束或多阶段重编号并同步规格。

### 5.3 为什么 903 通过仍找到问题

通过说明已有断言的行为成立，不等于所有产品要求都被断言。此次漏点集中于跨组件动作次序、默认值、非筛选 URL 变化、演示/真实展示差异；这些都能在服务端数据逻辑正确时存在。测试体系无需推倒，应该用此次明确反例补覆盖。远端 CI、历史迁移和真实生产验收又分别针对不同对象，必须继续保留独立状态。
