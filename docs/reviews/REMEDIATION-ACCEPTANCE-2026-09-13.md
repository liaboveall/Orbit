## 确认的实现缺陷

### AC-01 · P2 · 认证超限请求错误地返回 500（D4 重新打开）

位置：`src/server/auth/body-limit.ts:51`、`:97`，`tests/unit/auth-body-limit.test.ts`。

以合法 JSON 构造约 70KB 的认证请求，直接调用真实认证 POST 路由：不声明 Content-Length → **500**；声明 10 字节但实际超限 → **500**；明确声明 70000 → 413。真实流已限长，但流异常由 Better Auth 当作服务器异常处理，客户端输入导致错误日志与 500。声明和实际流两条路径没有统一失败语义。

现有两个相关单测使用全零字节（本来就不是合法 JSON），仅断言 `request.json()` 抛错，并由假 handler 返回 200。即便去掉限制，非法 JSON 也会抛错，因此它们不能证明超限拦截正确。

返工：使用可识别的超限信号，在库吞掉异常/转换响应的情况下仍可靠返回 413；保留字节上限、流取消和原请求 abort。以合法超限 JSON 验证真实 handler 的 413、消费有界及取消；合法小请求继续通过，移除限流实现后相应回归必须失败。

证据：`artifacts/acceptance-20260913/auth-probe.ts`、`auth-probe.json`、`auth-probe.log`。本次探针前后两库内容指纹一致。

### AC-02 · P2 · SMTP 总超时未关闭实际连接（D3 重新打开）

位置：`src/server/auth/email.ts:118`，安装版本 nodemailer 10.0.1 的 `dist/esm/smtp-transport/index.js:332`。

本机 SMTP 协议替身立即 greeting，此后每 8 秒回应一个阶段，避免触发 15 秒空闲超时。真实 `createEmailSender` 在约 **20213ms** 报错，但报错后 **仍有 1 条存活连接**。探针自行销毁了这条连接并关闭自己的服务器。

非连接池 SMTP transport 的 `close()` 只释放 OAuth 监听并发出 close 事件，没有关闭每次 send 内创建的连接。因此 Promise.race 只限制调用方等待，不满足“总预算到期结束底层工作”的交付承诺。原新增 SMTP 测试只覆盖 10 秒无 greeting，不能验证此路径。

返工：为每次发送建立真实可取消的资源生命周期；总预算到期关闭该次传输，避免影响其他发送。测试慢速持续推进场景，验证超时后套接字关闭、不会继续投递，并验证正常邮件与下一次发送。

证据：`artifacts/acceptance-20260913/smtp-probe.ts`、`smtp-probe.json`。仅使用本机协议替身及虚构收件人，没有发送外部邮件。

### AC-03 · P2 · 创建表单的取消/收起绕过草稿保护（B6 重新打开）

位置：`src/features/projects/project-create-form.tsx:352`、`src/features/projects/project-list-client.tsx:217`、`:275`；任务创建有同类直接回调路径。

四类表单已注册脏状态，程序化路由也已有统一入口；但项目创建的“取消”直接调用 onCancelled，父组件直接 setCreating(false)；“收起表单”也直接卸载表单。两条路径没有使用放弃确认。仅安装导航监听不会拦截组件内按钮卸载。

生产构建浏览器实测：创建独立测试用户，打开空项目页，点击“创建第一个项目”，填写项目名称后点击“取消”；确认弹窗次数 **0**，项目名称输入框消失。补充用例按正确期望失败，随后精确清理本次用户；两库内容指纹一致。项目取消为动态复现，收起与任务创建同类路径为源码核查。

证据：`artifacts/acceptance-20260913/draft.spec.ts`、`draft.log`、`browser-results/` 中的 observed 附件与 trace。

返工：将关闭、取消、收起以及路由离开纳入一致的放弃确认；用户拒绝时保留完整字段，接受后才卸载；保存成功后关闭不应再次确认。覆盖项目与任务创建，以及多 Provider 同时存在时只弹一次确认。

## 验收证据和范围缺口

### AC-04 · P2 · N01 只有接线，没有约定的故障恢复验收

`retry` 接线已修，不能据此判定实现错误；但关闭报告明确承认端到端测试被移除，将服务端故障注入留作“立项”。拦截 HTTP 500 没触发渲染边界，只能说明该注入方式不适用，不能证明本地无法完成验收。

返工：建立仅测试环境可用的确定性服务端渲染故障注入，证明边界出现、点击重试产生新请求、故障解除后恢复真实内容。生产构建不得暴露故障注入入口。在此之前记录为“实现已改、验证待完成”，不能作为已验证闭环。

### AC-05 · P2 · 关闭记录与原始证据不一致

- 关闭报告引用 `g6b-e2e-final.log` 证明全绿，实际文件是 **2 failed / 76 passed**，包含 `ELIFECYCLE` 退出 1，但末尾另写 `E2E_EXIT=0`。另一个 `g6b-e2e-rerun.log` 才记录 **77 passed**。不能仅按手写退出码或 passed 数判定成功。此处有有效复跑证据，不应误报成“Agent 从未跑过成功的 E2E”。
- 报告与 PROGRESS 写 31 个复合子项，JSON 实际有 **38** 个（F31=13、F33=6、F34=9、F35=10）；F01/F15/F19/F40/F41 没有指导要求的子项记录。F31 存在 deferred 子项，父组仍标 fixed、remainingLimitations 为空。
- `planning/backlog.json` 的具体任务已恢复 done，但顶层 latestReview 仍指旧审查并写“业务未修复”。README、PROGRESS、台账和任务总状态未形成一致快照。

返工：从真实日志自动汇总测试结果、退出码和分组/子项数量；引用正确的完整日志并记录执行时源码摘要。保留失败日志作为历史，不覆盖成成功。每个复合项对照原始要求补全子项，父状态反映未完成子项；区分本地待完成工作与确实依赖外部环境的工作。

### AC-06 · 验收阻断 · 调试清理误删历史测试数据尚未闭环

交付报告 §5.6 自述：临时调试清理误删了 18 个历史合成用户的 Account/Session/IdempotencyRecord 行。该事件违反“只清理本次夹具、保留已有数据”的执行约束。即使是合成数据，也会改变后续基线；账户和会话行不是无影响的临时文件。

本轮没有独立证明历史受影响行数、内容或恢复情况，不能扩大该自述为已核实的全部影响范围。当前测试前后指纹一致，只证明**本次**没有净变更，不能证明交付全过程未误删。

返工：给出触发脚本/命令、清理谓词、时间、可核验的影响范围和修复措施；若有既有备份，先只读核对恢复方案，不自动回填或猜造账户/会话数据。将当前运行唯一标识、精确 ID 集合和异常路径清理纳入防误删检查；明确该历史事件无法恢复或核验的部分，不能以重新采集基线当作事故已解决。
