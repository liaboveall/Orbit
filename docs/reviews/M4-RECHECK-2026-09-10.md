## 当前应优先处理的具体阻断

### B01 · P1 · 邀请页无法编译，生产构建和实际访问失败

`src/features/invitations/InviteAccept.tsx:86` 在 imports、类型及函数声明之后又写了一次 `"use client"`，Next 构建报：

> The "use client" directive must be placed before other expressions.

文件顶部已有正确指令，应修正错误的第二条声明，而不是忽略检查。`src/app/invite/page.tsx` 还保留多个未使用导入、空对象 PageProps 和未使用的 sessionUser；`member.service.ts:7` 的 ActivityEntry 未使用。lint 共 7 errors、9 warnings。本轮浏览器/HTTP 确认 `/invite` 返回 500。

### B02 · P1 · 新旧邀请协议没有贯通，匿名用户无法正确进入登录流程

- `src/server/modules/invitation/service.ts:157` 仍返回 `/invite/${token}`；客户端改成只读 hash/sessionStorage，而对应旧动态页面已删除。
- `src/features/invitations/InviteAccept.tsx:192–194` 收到 401 后执行 `window.location.assign(returnPath)`；新页面传入 `/invite`。这会回到同一邀请页，而不是 `/auth/login?returnTo=...`。
- 新 `/invite/page.tsx` 固定传 isLoggedIn=false，客户端又不使用此属性，总是显示“接受邀请”，没有原先匿名登录入口。

修复编译后仍需完整验证“创建链接 → 匿名打开 → 登录/注册 → 返回邀请 → 接受”，不能只测直接调用 API。此次已添加 no-referrer 元数据与 hash 清除，是局部进展，不能作为整个 R02 通过的证据。

### B03 · P1 · 新迁移不可执行，清理逻辑可能把已用邀请重新开放

文件：`prisma/migrations/20260910001346_add_invitation_accepted_constraint/migration.sql`。

隔离事务复验结果：

1. 执行完整 SQL 返回 PostgreSQL **42601：syntax error at or near "XOR"**。
2. 单独安装前面的触发器后，插入合法未使用邀请返回 **42703：record "new" has no field "acceptedat"**；原因是 NEW.acceptedAt/acceptedById 没有正确引用大小写列名。
3. 两库目前均未安装此迁移；独立写入 acceptedAt 非空、acceptedById=null 仍成功。

此外，`scripts/cleanup-invitation-constraints.ts:38` 判断条件为：

```sql
("acceptedAt" IS NULL) != ("acceptedById" IS NOT NULL)
```

该条件恰好选中“两字段同空或同非空”的合法行，而不是非法行。后续把两字段置空，会把合法已消费邀请变回未消费。这是代码审查确认的危险逻辑，本轮**没有执行该清理脚本**。

重新设计约束和定向数据修复：按规范添加真正的 CHECK，处理 acceptedById 外键策略；不得通过把已用邀请重置未用来“清理”。对未使用、已使用、两个非法组合分别验证，确认历史已用 token 不会恢复可用。新维护脚本使用的 `@prisma/client` 默认导入及无 adapter 初始化也需与当前 Prisma 7、自定义生成路径和 `.env.local` 加载方式核对。

### B04 · P1 · 注释不等于行锁，同一令牌仍可多人消费

`src/server/modules/invitation/service.ts:259–260` 注释写“FOR UPDATE”，实际只是 Prisma findFirst + orderBy，没有获取任何行锁。360 行无条件 update 后检查 acceptedAt 是否为空，也不能识别竞争：两个请求都刚把它写成了非空。

复用上次可控锁竞争探针，两请求都成功、两人成员关系都存在。应在 Project 行锁内重新读取状态并完成消费，与撤销、归档、配额检查串行化。正式测试 551—565 行附近仍只要求“至少一次成功”和“成员数等于成功数”，必须改为恰好一个成功。

### B05 · P2 · 配额提前拒绝正常用户与 owner

`src/server/modules/invitation/service.ts:36, 318–325` 把 MAX_ACTIVE_INVITATIONS=10 同时用作成员配额。独立构造 owner+10 个成员，共 11 人，再接受邀请返回 422；owner 接受也返回 422，因为已有身份判断在配额之后。仍未达到规定的 20 人上限。

必须拆分两个配额常量：有效邀请最多 20；项目人数含 owner 最多 20。已有 owner/member 不新增人数，不应因新增成员配额检查而被拒绝。
